# Revue des amendements — builds Tauri multi-client

Les propositions ci-dessous ont été évaluées et intégrées, avec les nuances
indiquées, dans le plan canonique
[`specs/tauri-multi-client.md`](../../specs/tauri-multi-client.md).

| Proposition | Décision | Traitement |
|---|---|---|
| Workspace Cargo à la racine avec lockfile et target partagés | **Retenue** | Centraliser les dépendances Rust et réutiliser le cache de compilation. Vérifier explicitement la compatibilité des chemins Tauri/Gradle générés avant de généraliser. |
| Desktop est principalement un client de test | **Retenue** | Le plan prend les apps métier (teacher et futurs clients) comme produits natifs de référence ; desktop conserve son shell et ses usages de test. |
| Versionner `gen/android` | **Rejetée** | Le projet Android est régénérable ; ignorer `gen/android` et documenter la procédure reproductible d'initialisation. |
| Convention d'identité et de noms Cargo | **Retenue avec exception** | Utiliser `io.attendancy.<role>`, `attendancy-<role>` et `attendancy_<role>_lib` pour les nouveaux shells. Garder `io.attendancy.app` pour desktop afin de préserver son identité existante. |
| Reprendre `tray-icon` dans teacher pour unifier les features | **Écartée** | Centraliser les versions dans `[workspace.dependencies]`, mais activer par shell uniquement les features réellement nécessaires. Une feature inutile peut ajouter des dépendances et du code ; le partage du workspace ne justifie pas de l'activer artificiellement. |
| Limiter le premier build Android à `aarch64` | **Retenue** | Cible initiale du build de développement ; ajouter d'autres ABI uniquement pour un besoin identifié. |
| Builds obligatoirement séquentiels avec target partagé | **Nuancée** | Le plan impose de ne pas paralléliser avant validation. La sérialisation exacte dépend des verrous Cargo et de l'orchestration Tauri/Gradle ; la vérifier au lieu de présumer que Cargo verrouille tout le dossier. |
| Tester tous les shells après évolution du lockfile partagé | **Retenue** | Après un `cargo update` ou changement du lockfile racine, lancer les vérifications/builds ciblés de chaque shell. |
| Ne coder aucun chemin global `target/` dans `tools/tauri` | **Retenue** | L'outil doit résoudre ou recevoir le chemin de sortie. Les APK restent sous le projet Android généré de chaque application. |
| Uniformiser les features pour éviter leur dérive | **Nuancée** | Centraliser les versions et documenter les features de chaque shell ; ne pas exiger un ensemble identique. Vérifier l'usage des features et l'économie réelle du cache, notamment par cible. |

## Points de vérification ajoutés au plan

- Vérifier que Tauri et le projet Android généré trouvent les artefacts Rust
  avec le workspace et le `target-dir` racine.
- Confirmer les chemins de sortie Cargo des bundles desktop et garder les
  chemins des APK attachés au `gen/android` de leur app.
- Vérifier que les instructions de clone/setup régénèrent correctement
  `gen/android`, sans dépendre de fichiers générés versionnés.
- Tester les builds desktop et teacher séparément avant d'essayer leur
  exécution simultanée.
